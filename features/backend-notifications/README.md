## Суть

Владелец/менеджер не понимает, что происходит с командой, без обхода каждого визита руками. Первая версия — лента апдейтов по визитам: колокольчик с индикатором непрочитанного, модалка со списком, отдельный полноэкранный список «show all». Только про команду; масштабирование на инвойсы/клиентов (клиент посмотрел инвойс, клиент оплатил) — потом.

**Риск дублирования:** Никита сразу отметил (02:13), что рядом живёт TODO-список с той же идеей «подсветить места, где нужно действие» — важно не получить два места, решающих одну задачу.

## Решено

- **4 типа событий в MVP**, все инициируются только worker'ом, не владельцем (22:25): начало визита, конец визита, принятие приглашения в команду, визит не начат вовремя (`hasn't started yet` = `now − scheduled start`, 22:57). Расписание есть у **всех** визитов — в отличие от джобов (22:45).
- **Группировка по визиту:** одна карточка на визит, показывается только **последнее** событие независимо от прочитанности (26:36). С бэкенда — последнее событие + флаг прочитанности (27:16).
- **Прочитанность — по явному действию в ленте:** тап по нотификации (открывает визит) либо `mark all read` (28:29). Открытие визита из другого места прочитанным **не** считается — предложение Никиты привязать read к визиту (27:35) было отклонено.
- **Только онлайн.** Оффлайн — не старый стейт, а всегда ошибка/заглушка «подключитесь к сети»; сохранённого стейта нет вообще (16:22, 17:04).
- **Без фоновой синхронизации.** Фетч при открытии ленты; колокольчик дополнительно обновляется при навигации по страницам и рефрешах (39:25). Если список открыт долго и данные изменились — устаревание принято как норма для первой версии (39:03).
- **Пуши и бейдж на иконке приложения — не в скоупе.** Бейдж требует пуша на каждое изменение, это отдельная большая история (18:23, 20:37).
- **Действия из ленты:** клик по ячейке → визит (для `join` → вкладка команды), `call` → звонилка с номером, `assign visit` → schedule для переназначения (24:22). Звонок на десктопе под вопросом: либо `tel:`-ссылка, либо просто показать номер для ручного набора (04:26–06:45).
- **Устаревшие нотификации** (владелец перепланировал/закрыл визит сам) — в MVP не обрабатываем: `MikeStartedVisit` будет висеть как есть (42:28).
- **Два экрана:** модалка с лимитом (Анастасия — 10–15, Максим — 20–30) + отдельный полноэкранный список с той же фильтрацией `all`/`unread`, попасть можно только через `show all` (34:21).

## Дизайн

**Макет:** [🖥️ Notification Center](https://www.figma.com/design/fxMR8mhdMJkxXVnWust6fm/%F0%9F%96%A5%EF%B8%8F-Notification-center?node-id=2041-17627&m=dev) (страница `Notification center`; снят через Figma MCP 2026-07-27). Состав: секция `Components` (варианты айтема, unread-dot, call-контролы), `Notifications types` (4 типа), `Notification center states` (заполненный/короткий/пустые/загрузка), полноэкранный список, мобильная секция.

**Экраны и состояния:**

| Состояние | Что показывает |
|---|---|
| Popover `Filled_full` | 10 айтемов + футер `Show all notifications`; шапка `Inbox` / `Unread N` / `Mark all read` |
| Popover `Filled_few` | та же шапка, 2 айтема, без футера |
| `Empty inbox` | «Your team's day shows up here / See when your techs start and finish visits, in real time.» — в двух вариантах: с кнопкой `Invite your team` и без неё |
| `Empty Unread` | «No unread updates» (таб `Unread` активен, `Mark all read` скрыт) |
| `Type=Loading` | skeleton-строки вместо айтемов |
| Полный экран | `Back`, заголовок `Notifications`, `Mark all read`, табы `All` / `Unread N` — то есть на полном экране первый таб называется `All`, а в поповере `Inbox` |
| Мобильный веб | поповера нет вообще: «Открываем сразу полноэкранные нотификации без прослойки в виде поповера» (аннотация на макете) |

**Анатомия айтема** (`Notification Item`, варианты `Start` / `Finish` / `Invite` / `Not started`, база `Default` / `Negative` / `Loading`):

- строка заголовка: **имя воркера в сокращённой форме** (`Mike J.`, `Sarah B.`) + текст события (`started the visit`, `finished the visit`, `joined your team`, `hasn't started yet`);
- вторая строка (кроме `Invite`): время визита `8:00 - 9:30 AM` · услуга `Hedge Trimming` · адрес `1247 Westborough Drive`;
- справа: время события — относительное (`2 min ago`) либо дата (`Jul 14`, `Dec 1, 2025`) — и **unread-dot**: `Default` зелёный, `Negative` красный;
- у `Not started` — чип `24 min late` рядом с датой;
- действия: `Assign a visit` (у `Invite`), `Call <Имя>` + отдельно показанный номер `(123) 456-7783`, либо `Open visit` — вариант без номера телефона (ровно тот случай, который Никита описывал на груминге: у техника нет номера → менеджер открывает визит);
- непрочитанный айтем имеет подсветку фона, есть отдельное hover-состояние.

**Что дизайн решает за груминг:**

- **Индикатор — и точка, и число.** На колокольчике (веб-сайдбар и мобильная шапка) — зелёная точка без цифры; в табе `Unread N` — **число** (`Unread 5`, `Unread 2`). То есть открытый вопрос «точка или цифра» (43:17) снимается компромиссом, но требует от бэкенда **обе** величины: дешёвый флаг для точки и счётчик для таба.
- **Пагинация подтверждена:** поповер — 10 айтемов, дальше `Show all notifications` → полноэкранный список. Совпадает с обсуждением лимита 10–15 / 20–30.
- **Пустое состояние для аккаунта без команды** — отдельный вариант с CTA `Invite your team`, то есть вопрос Андрея про владельцев без воркеров (46:36) в макете закрыт.

**Расхождения и вопросы к макету:**

- В `Filled_full` **два айтема `Sarah B. hasn't started yet` по одному и тому же визиту** (одинаковые время, услуга, адрес, дата `Jul 12`) — один с `Call Sarah`, другой с `Open visit`. Либо это демонстрация двух вариантов компонента в одном списке, либо противоречие принятой на груминге группировке «одна карточка на визит» (26:36). Нужно подтвердить у дизайнера.
- **`24 min late` — кто считает?** Если значение приходит с бэкенда, оно устареет в открытой ленте; если считает клиент, в payload нужен `scheduledStartAt`. Груминг определил величину как `now − scheduled start` (22:57), но не сказал, где она вычисляется.
- Время события подаётся и относительно, и абсолютно — значит бэкенд отдаёт только timestamp, форматирование на клиенте (уже так: `CreatedAt` в DTO).

## Гэпы до требований груминга

1. **Типы событий.** `NotificationType` содержит только `FirstPaymentReceived`, `PspOnboardingCompleted`; `NotificationSource` — только `Payments`, `Stripe`. Нужны 4 типа визитов/команды и источник Jobs/Team.
2. **Нет группировки по сущности.** У `Notification` нет `EntityId`/group key — «одна карточка на визит» без нового поля и индекса не реализуется. Это главная схемная правка.
3. **Нет ручки для колокольчика** — ни `unread-exists`, ни `count`. Контроллер отдаёт только список и отметку одной записи. По макету нужны **обе** величины: флаг для точки на колокольчике и число для таба `Unread N`.
4. **Нет `mark all read`.**
4a. **Payload не определён.** По макету одному айтему нужны: сокращённое имя воркера, тип события, `scheduledStartAt`/`scheduledEndAt` визита, название услуги, адрес, телефон воркера (его наличие переключает `Call` ↔ `Open visit`), идентификатор визита для перехода. Ничего из этого в текущих payload'ах (`FirstPaymentReceived`, `PspOnboardingCompleted`) нет — контракт надо проектировать с нуля; сериализация в jsonb с camelCase уже настроена (`NotificationDispatcher`).
5. **Нотификации по визитам не создаются.** `INotificationDispatcher.CreateNotification` вызывается всего из двух мест — `Invoices.Payments/PaymentsService.cs:301` и `PaymentIntentsService.cs:591`. Проводки от `JobDomainEvent` в модуль нет.
6. **`hasn't started yet`** — событие не от действия пользователя, а от истечения времени: нужен планировщик (в модуле уже есть Hangfire) и правило отмены/перезаписи при старте визита или переносе.
7. **Push «worker joined» живёт отдельно** от модуля: `Invoices.Api/Services/TeamNotificationService.cs` шлёт пуш только владельцам с iOS-линком и в ленту ничего не пишет.
